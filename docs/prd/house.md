# House Design — PRD

**Related:** [../../PRD.md](../../PRD.md)

**Status:** V2 — parametric room/floor entry (forms, and now direct drag-to-draw/move/resize on a 2D plan and click-to-edit in the 3D view) rendered as a 3D model, both interior and exterior, plus a 2D CAD-style plan.

## Current scope

Planning a real house/renovation — not a file importer, not a furniture-shopping catalog. Rooms/floors can be described through forms, drawn/dragged directly on a 2D plan, or edited by clicking their wall/door/window/furniture/light-fixture mesh in the 3D view; the app derives and renders the 3D model (and the 2D plan) from that data either way.

- **`house_projects`**: one row per house/renovation design (name, notes, `roof_type` flat/gabled/hip, `roof_pitch_degrees`). Supports comparing more than one design, same as every other module here being a list rather than a singleton.
- **`house_floors`**: belongs to a project. `level` (0 = ground, negative = basement, positive = upper) orders floors vertically; `floor_height` (meters) is the default wall height for its rooms.
- **`house_rooms`**: belongs to a floor. `x`/`z` position + `width`/`depth` (meters) on the floor's plan; `wall_height` optionally overrides the floor default; `color` optionally overrides the type-based default used in the viewer; `material` (matte/satin/gloss/metal, optional) overrides the default wall roughness/metalness preset — see "Materials" below.
- **`house_openings`**: belongs to a room. A door or window on one of the room's 4 walls (`north`/`south`/`east`/`west`, matching `RoomWalls`' wall placement convention), positioned by `offset` from that wall's start corner. `width`/`height`/`sill_height` default per opening `type` (door vs window) in the viewer when left blank. `style` (hinged/sliding/french/flush/louvered for doors; fixed/casement/sliding/awning/louvered for windows) is free text at the DB level — the valid set depends on `type`, so it's validated against `DOOR_STYLES`/`WINDOW_STYLES` at the action layer, not a DB enum. Style doesn't change the viewer's rendering, just the recorded data.
- **`house_stairs`**: belongs to a project (not a floor — it spans two). One row is one straight flight: `from_floor_id`/`to_floor_id`, a starting `x`/`z`, `width`, horizontal `run`, and `rotation_degrees` for its direction. A switchback stair is entered as two or more adjacent flight rows — there's no single multi-turn stair entity. `railing_side` (none/left/right/both, default both) and `railing_height` control a simple rail rendered alongside the flight.
- **`house_fixtures`**: belongs to a floor. A point-like utility element (water inlet, sump, septic tank, overhead tank, drain outlet, electrical panel) not tied to any one room — just a `category`, `name`, and `x`/`z` position.
- **`house_wall_styles`**: belongs to a room. An override for one of its 4 walls — `open` (no wall), `railing` (a low kick wall + rail, with `railing_height`), or `painted` (still solid, but `color` overrides the room's own color for just this wall). Used for balcony edges and open-concept landings/hallways overlooking a floor below. No row means solid in the room's own color; at most one row is expected per room+wall (not DB-enforced — the renderer uses the last one found, same pattern as `house_openings`).
- **`house_furniture`**: belongs to a room. A simple placeable item (bed, sofa, table, chair, wardrobe, desk, TV unit) rendered as one colored box, not a 3D model. `x`/`z` are room-relative (see the note below) and `rotation_degrees` is its orientation (0 = width along +x). `material` works the same as on rooms.
- **`house_light_fixtures`**: belongs to a room. An actual light source (ceiling/wall/pendant/floor lamp), not just a marker — rendered as a small emissive marker plus a real `pointLight` that illuminates the room. `height` (mounting height from the floor) defaults per `type` when left blank; `x`/`z` are room-relative, same as furniture.

**A note on `x`/`z` conventions** — they differ by entity and it matters when reading/writing data directly: room/fixture/stair coordinates are **absolute** floor-plan coordinates (same origin as the floor itself); furniture/light-fixture coordinates are **room-relative** (added to the room's own `x`/`z` when rendering); opening `offset` is relative to its *wall's* start corner. This wasn't chosen for consistency — each matches how that entity is most naturally described (a fixture like a sump isn't "in" any one room, but a lamp obviously is).

**Exterior is derived, not separately modeled**: the perimeter walls and roof are computed from the union bounding footprint of each floor's rooms, not entered as their own data — this keeps the interaction to "describe rooms" only while still producing a full exterior+interior model. The roof sits above the topmost floor's bounding footprint. `hip` renders using the same two-panel gabled shape as `gabled` for v1 — a documented visual approximation, not true hip-roof geometry.

**Editing**: rooms/floors/projects all support update, not just add (unlike most of this app's otherwise add-only modules) — getting dimensions right through iteration (e.g. a room entered at 30m, later corrected to 35m) is the core workflow here, so it's a first-class requirement. A room can be edited three ways, all converging on the same `updateRoomAction`: a pre-filled form (re-renders the 3D/2D views on save), dragging its body/corner handle directly on the 2D plan (`floor-plan-2d.tsx`, see "2D plan view" below), or clicking its wall in the 3D view to open the same form pre-filled (see "Click-to-select" below).

Units are meters throughout.

## Rendering

`@react-three/fiber` + `@react-three/drei` (`Canvas`, `OrbitControls`, `Grid`). Each room renders as 4 wall meshes around its perimeter (not a solid block) so room boundaries are visible from outside. `service/model.ts`'s `getHouseModel()` does all the geometry assembly (floor Y-offsets, footprint bounding box, stair flight endpoints) as plain, unit-tested functions — the client viewer only turns those numbers into meshes.

**Openings are real cut holes**: a wall with one or more openings is CSG-subtracted (via `three-bvh-csg`'s `Brush`/`Evaluator`/`SUBTRACTION`) into an actual hole, not a solid box with a panel glued on top — see `computeOpeningCutout` in `wall-cutout.ts` for the pure cutout-box geometry (unit-tested independently of Three.js/WebGL) and `Wall`'s `cutoutGeometry` in `house-viewer.tsx` for the CSG evaluation itself. A door/window leaf still renders as a thin colored panel (`OpeningPanel`), but now recessed inside the real hole rather than floating just outside a solid wall. A wall with no openings skips CSG entirely and keeps the plain box it always had, since boolean evaluation isn't free. This pure cutout-geometry helper deliberately lives in the app layer (`src/app/(protected)/house/`), not `modules/house/service/` — importing a runtime value (not just a type) from the house module's barrel would pull its service/query code, and therefore the native SQLite binding, into the client bundle (see AGENTS.md's client-import rule).

**A stair flight is a single sloped box** from its `fromFloor` to its `toFloor` — no individual treads/risers. A switchback stair is two or more flight rows placed adjacently by hand (matching x/z/rotation), not a single turning entity. Its rail (if any) is drawn in the flight's own tilted local frame so it follows the slope for free.

**A railing wall is a kick wall + one rail bar + 2 corner posts** — a visual approximation, not individual balusters. Same v1-approximation spirit as the opening panels and the hip roof.

**The 3D viewer has a 3D/North/South/East/West toggle**: North/South/East/West are `OrthographicCamera` views (via `@react-three/drei`) looking straight at one exterior face — flat elevation-style views, not full 2D CAD elevation drawings (no dimension lines). Rotation is locked in these modes (`OrbitControls`' `enableRotate={false}`); pan/zoom still work.

**The 3D viewer's camera refits when the model's footprint size changes**: the 3D-mode `PerspectiveCamera` (a `@react-three/drei` component, not `Canvas`'s `camera` shorthand prop) is keyed on the rounded footprint size, so it remounts — and re-applies its initial framing — only when the size actually changes, not on every unrelated re-render (which would otherwise fight the user's manual orbit).

**Lighting/materials are tuned for presentability, still no textures or HDRI**: `Canvas shadows` + a shadow-casting `directionalLight` (targeted at the model's footprint center, not world origin) give real cast shadows; `ContactShadows` (procedural, no image assets) grounds the building against the grid. Every mesh has `roughness`/`metalness` tuned per material family (matte walls/roof, glossy window panels, brushed-metal railings) instead of the flat default. Deliberately **not** using drei's `Environment` — its HDRI `preset`s fetch from a third-party CDN at runtime, a network dependency this local-only app shouldn't take on by default. Also deliberately **not** using drei's `SoftShadows` — it works by mutating `THREE.ShaderChunk` globally, which breaks (`WebGL: program not valid`, cascading) under this app's `next dev` Fast Refresh; the standard PCF shadow map from `Canvas shadows` is used instead.

**Furniture is one box per item** — no sub-parts (a bed isn't a frame + mattress + pillow), no 3D model library. Category only changes its default color.

**A light fixture is a real light, with a performance guardrail**: each renders a `pointLight` at its resolved mounting height, so a room actually gets brighter/tinted by its fixtures — but none of them `castShadow`, since a shadow-casting point light is a full extra shadow-map render pass and a room can have several fixtures; the single `directionalLight` in `Scene` is the only shadow caster.

**Materials are a user-selectable finish preset, still no textures**: a room or furniture item's optional `material` (matte/satin/gloss/metal) selects a `roughness`/`metalness` pair from `MATERIAL_PRESETS` in `house-viewer.tsx`, used instead of the fixed per-family constants described above. This is still just a different PBR tuning on the same `meshStandardMaterial` — no textures or HDRI, same policy as the rest of this section. Picked via `ColorSwatchPicker` (`src/components/ui/color-swatch-picker.tsx`) for color and a plain `<select>` for material, on the room/furniture/wall-style forms; takes effect on save like every other edit in this app, not as a live preview before submitting.

**Click-to-select in the 3D view**: every wall, opening, furniture item, and light-fixture marker has an `onClick` (`selectableProps` in `house-viewer.tsx`), reported up as a `HouseSelection` to `HouseWorkspace`, which opens that entity's existing edit dialog pre-filled — the same dialog its table row's "Edit" button opens, just driven externally via the dialogs' now-optional `open`/`onOpenChange` props instead of their own internal state. A wall's "options" are its room's — clicking any wall opens the room dialog (color/material/dimensions), there's no separate per-wall entity to edit beyond `house_wall_styles` overrides, which stay table-only.

## 2D plan view

`floor-plan-2d.tsx` — a top-down SVG of one floor, `viewBox` directly in meters (no pixel/meter scale factor), `vectorEffect="non-scaling-stroke"` on every line so stroke width stays visually constant regardless of room size or zoom. Pure geometry (footprint bounding box, an opening's indicator-segment position, drag-rect normalization, grid-snapping) lives in `plan-2d-geometry.ts`, unit-tested the same way as `wall-cutout.ts` and `service/model.ts` — and, same reasoning as `wall-cutout.ts`, deliberately duplicates `computeFootprint`'s math rather than importing it from `modules/house/service/model.ts`, to keep the native SQLite binding out of the client bundle.

- **Rooms** render as a rect (fill = the room's own color or the type default, stroke = current text color) with its name centered, plus two dimension lines (width above, depth to the left — extension line + tick marks + a rotated label for the vertical one) offset 0.5m outside the room.
- **Openings** render as a short colored segment (brown = door, cyan = window) along the room's edge at the opening's real wall/offset/width — `computeOpeningSegment` mirrors `getWallGeometry`'s wall-side convention from `house-viewer.tsx`.
- **Furniture** renders as a small rect inside its room, positioned by the item's room-relative `x`/`z` (same convention as the 3D view) — click to open its edit dialog, same as clicking it in 3D.
- **Draw-to-create**: dragging on empty canvas draws a rubber-band rectangle; on release (if at least 0.3m in both dimensions — smaller counts as a stray click, not a draw) it calls `addRoomAction` directly (not through a form/`useActionState`, since there's no form here) with the drawn `x`/`z`/`width`/`depth`, a default name ("New room") and type (`other`), snapped to a 0.1m grid — then immediately opens the new room's edit dialog via the returned id (`AddRoomState.id`, added specifically to support this caller).
- **Drag-to-move/resize**: dragging a room's body translates its `x`/`z`; dragging its bottom-right corner handle resizes `width`/`depth` (origin fixed at top-left — the simplest correct resize, not 4-handle/8-handle). A live local-state preview follows the pointer during the drag; releasing calls `updateRoomAction` directly with the full room row (not a partial patch — `roomSchema`'s update replaces every field, so `notes` etc. must round-trip even though only geometry changed), grid-snapped to 0.1m. A drag below a small movement threshold is treated as a plain click (opens the edit dialog) rather than a no-op move, so clicking a room still works.
- **Furniture catalog + drag-and-drop**: `furniture-catalog.tsx` renders `FURNITURE_CATEGORIES` as native-HTML5-draggable chips (no drag/gesture library — a single-item drag doesn't need one). Dropping one onto the plan resolves which room's rect contains the drop point (`findRoomAt`), computes a category-default size (`FURNITURE_DEFAULT_SIZE`) clamped to fit inside that room, and calls `addFurnitureAction` directly — same "call the Server Action directly, use the returned id to auto-select" pattern as draw-to-create. There's no equivalent 3D-view drop target: the 3D view renders every floor of the project stacked, so a screen-space drop point is ambiguous about which floor's ground plane it should hit-test against — the 2D plan (always scoped to one floor) is the well-defined place for placement, deliberately narrower scope than a literal reading of "drag furniture into a 3D room."

## Export

Both viewers have their own "Export" button, each reading from a ref they already own — no shared state, no server round trip. The 3D view (`HouseViewer`) reads the R3F `Canvas`'s underlying `<canvas>` via `onCreated`'s `state.gl.domElement` and calls `.toDataURL("image/png")` (`gl={{ preserveDrawingBuffer: true }}` on `Canvas` is required for this to not read back blank — WebGL clears its buffer post-render otherwise). The 2D plan (`FloorPlan2D`) clones its `<svg>`, sets an explicit `xmlns` (needed for the file to render correctly outside a browser tab), and serializes it via `XMLSerializer`. Both trigger a download through a shared `downloadDataUrl` helper (`download-file.ts`) — a temporary `<a download>` click, standard client-side pattern, no library. This stands in for custom3dbuilder.com's "save/share design via email" and "request a quote" — this is a single-user local-only app with no vendor to send a quote to, so those were deliberately not built literally.

## Deferred

No delete (consistent with the rest of the app). No individual stair treads/risers or balusters, no full 2D CAD *elevation* drawings with dimension lines (the North/South/East/West 3D-view toggle is still a flat orthographic camera look, not linework — the new 2D plan view above is a separate top-down thing), no furniture sub-parts or 3D model library, no shadow-casting light fixtures, no file *import*, no multi-user sharing, no furniture drag-and-drop onto the 3D view (see "2D plan view" above for why). Revisit if/when they come up.
