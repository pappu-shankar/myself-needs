## Notable implementation decisions not called out in the original plan

- **Liability sign convention**: asset accounts store a positive balance, liability accounts (`credit_card`/`loan`) store a *negative* balance (amount owed). `createAccount` negates whatever positive "amount owed" the form collects. This makes `getTotalBalance` a correct net figure via a plain sum, with no per-type special-casing anywhere else. See `docs/prd/finance/accounts-transactions.md` and `src/modules/finance/service/accounts.ts`.
- **Duplicate DOM ids across forms on one page**: `/finance` renders three forms (account/category/transaction) at once — an early version had two `id="type"` selects colliding. Fixed by prefixing each form's ambiguous field ids (`accountType`, `categoryType`, `transactionType`). Worth checking for whenever a page combines multiple forms with generically-named fields.
- **`@tanstack/react-table` is on v9, which has a different API from the v8 most training data/tutorials know**: no `useReactTable`/`getCoreRowModel`/standalone `flexRender`. Instead: `tableFeatures({...})` to opt into feature slots (core row model is built in, no opt-in needed), `useTable({ features, columns, data })`, and `table.FlexRender` as a method on the table instance rather than an import. Per-column `meta` typing goes through a `columnMeta` type-only slot on `tableFeatures(...)`, not global declaration merging (that needs 3 type params — `TFeatures, TData, TValue` — now, not 2). The installed package ships version-matched skills at `node_modules/@tanstack/react-table/skills/*/SKILL.md` (`getting-started`, `with-tanstack-virtual`, `table-state`, etc.) — read those (or the installed `.d.ts` files directly) before writing v9 table code instead of relying on remembered v8 patterns. `src/components/ui/data-table.tsx` renders virtualized rows as real `<tr>`/`<td>` with top/bottom spacer rows (not TanStack's own absolutely-positioned-`<div>` example) to keep native `<table>` semantics per `docs/design/accessibility.md`.
- **Budget `effective_from` comparisons are month-granularity, not exact-date**: the "Add budget" form defaults `effective_from` to *today* (matching the transaction/account forms' date-input convention), which is usually mid-month, not the 1st. `listBudgetsForMonth` (`src/modules/finance/db/queries/budgets.ts`) therefore compares `substr(effective_from, 1, 7)` against the target month's `YYYY-MM` prefix rather than the raw date — a budget added on the 23rd for "this month" needs to count as effective for the whole month, not just from the 23rd onward. Caught by browser-testing the feature end-to-end (a budget added mid-month silently didn't show up under a naive exact-date `<=` comparison) — worth re-testing if this query is touched.
- **`/finance/debts` is a real sub-route, not a section on `/finance`**: the PRD calls it "a dedicated Debts view" and it needs room for a full amortization table plus a prepayment calculator — cramming that onto the already-long `/finance` page would hurt more than a nested route costs. This is the first nested route under a module page; `calculators.md`/`insights.md`/`reports-allocation.md` already call for their own routes too, so more of these are coming. `SidebarNav`'s active-state check (`pathname.startsWith(href + "/")`) already highlights "Finance" correctly for any `/finance/*` route, no nav changes needed.
- **Amortization schedule is computed forward from the loan's *current* outstanding balance, not replayed from `original_amount`**: this reflects any prepayments already made without needing to reverse-engineer elapsed months from transaction history (recurring EMI tracking doesn't exist yet — that's step 5). `original_amount` is used only for the payoff-progress percentage. `service/loans.ts` has no imports at all (pure functions, no DB) specifically so a `"use client"` component can import it directly — importing it via the module's `index.ts` barrel from a client component would pull in every other service file's `getDb()`/native-binding import transitively and break the client bundle, same failure mode as the Server Action barrel rule in `docs/architecture/system-design.md`.
- **"Not yet logged" is decided by count, not by matching dates**: a recurring rule's due periods (`generatePeriodStarts` in `service/recurring.ts`) are computed purely from `start_date`/`frequency`/`end_date` up to today; separately, `countLoggedForRule` counts how many real transactions carry that rule's id via `finance_transactions.recurring_rule_id`. The oldest N periods are then treated as "logged" and the rest as due — there's no date-window matching between a period and the transaction that fulfilled it. This is deliberate: the PRD says the pre-filled confirm form's date is editable (e.g. rent paid on the 3rd instead of the 1st), so matching by exact date would misfire. The tradeoff: confirming a period always consumes the *oldest* outstanding one, even if a user picks a later date on the confirm form — there's no way to confirm periods out of order. Good enough for a single-user app with no reason to skip around; revisit if that assumption breaks.
- **`RECURRING_FREQUENCIES` grew two values (`quarterly`, `half_yearly`) beyond what step 5's PRD literally listed (weekly/monthly/yearly)**: insurance premiums are routinely quarterly or half-yearly, and the period-generation math (`addMonths` plus a `MONTHS_PER_PERIOD` lookup) already generalized to any month count for free, so extending the enum cost almost nothing and made both features more useful. `text(..., { enum: [...] })` in this codebase's drizzle-sqlite setup is TypeScript-only (no DB-level CHECK constraint — see the generated migrations), so widening it didn't need a migration for existing rows.
- **Insurance links to an *existing* recurring rule via a dropdown, not "create one inline"**: the PRD only requires the link to exist, not a specific creation flow. Building an inline rule-creation flow inside the insurance form would have duplicated the account/category/frequency inputs already on "Add recurring rule". Simpler and just as correct: add the recurring rule first (same form used for rent etc.), then pick it from `getRecurringRules()` when adding the policy.
- **Three current-value strategies, chosen strictly by type, per the PRD's own per-type table** (`getHoldingValue` in `service/investments.ts`): unit-priced types (equity/mutual funds/gold/bonds) use `units × latest investment_valuations row` (bonds have no `units`, so a null `units` is treated as 1 — the manually-entered valuation IS the total mark-to-market value, which is exactly what the PRD asks for without a schema special case); FD/RD use a compounded accrual estimate off `interest_rate`; chit funds and govt schemes fall back to plain net-cash-flow-to-date (money in minus money out), since the PRD explicitly says a govt-scheme holding "uses the same cash-flow mechanism as everything else" and the template's rate is reference-only, not part of a computed valuation. The UI labels each with its basis (`market` / `accrued est.` / `net invested`) rather than presenting all three as equivalent "current value" numbers, since they're not equally trustworthy.
- **FD/RD accrual compounds each contribution separately from its own date**, not one lump sum from the earliest cash flow: `computeAccrualValue` sums `principal × (1 + rate/100)^years` per contribution. This is what makes the exact same function correct for both a single-lump-sum FD and a drip of monthly RD installments without special-casing either — an RD's later installments haven't been compounding as long as its first, and this formula reflects that automatically.
- **`price-providers/` is a new top-level directory in the finance module, sibling to `service/`/`actions/`/`db/`**, not folded into `service/investments.ts`: it's the one piece of the finance module that makes an outbound network call, and the PRD is explicit that this must stay swappable behind a `PriceProvider` interface (so a future paid API for equity/gold can be dropped in without touching the holdings schema, UI, or any calculation) and must never be a background poll — isolating it makes both of those properties easy to audit at a glance rather than buried inside a service file that's otherwise pure DB reads/writes.
- **Scheme templates are seeded lazily on first read (`seedIfEmpty` in `db/queries/scheme-templates.ts`), not via a data migration**: `drizzle-kit generate` only diffs schema (DDL), and this project's migration discipline is "only ever run `drizzle-kit generate`" against the real encrypted DB (see `drizzle.config.ts`) — hand-writing a seed SQL file outside that flow risks desyncing the migrations journal. A `count() === 0` check before every `listSchemeTemplates()` call is negligible overhead for a single-user local SQLite file.
- **`xirr` (the npm package) ships no types and no `@types/xirr` exists**, so `src/types/xirr.d.ts` hand-declares its shape from the README — same pattern already used for `better-sqlite3-multiple-ciphers`. `computeXirr` wraps the call in try/catch and returns `null` instead of letting it throw: the package throws on fewer-than-2 transactions, all-same-sign amounts, all-same-day dates, or Newton's-method non-convergence, all of which are *routine* here (e.g. a holding whose current value was recorded but whose acquisition cash flow never was) rather than exceptional — the UI shows "—" for those, not a crashed page.
- **`computeXirr`/`computeIrr`/`computeCagr` (`service/returns.ts`) are pure, DB-free functions and deliberately not re-exported from the module `index.ts` barrel** — same reasoning as `service/loans.ts` (see step 4's note): a client component needs to import them from `service/returns` directly so it never pulls in the barrel's `getDb()`-touching service files into the client bundle. `service/investments.ts`'s `getPortfolioXirr`/per-holding XIRR (which *do* touch the DB) go through the barrel as normal.
- **Portfolio-level XIRR reflects whatever cash-flow data actually exists — it will look inflated for a holding whose current value was entered without ever logging its acquisition cost** (verified live: a mutual-fund holding with only a NAV-refreshed valuation and no contribution cash flow pulled the blended portfolio XIRR up, since its value counts as a costless "as of today" inflow). This isn't a bug to fix later — XIRR is only as good as its input ledger, same as any real portfolio tracker — but worth knowing so a surprising number during testing isn't mistaken for a calculation error.
- **The net-worth chart's line color is the app's existing `--primary` teal, not the dataviz skill's default blue** — a deliberate, *validated* choice, not an eyeball: `scripts/validate_palette.js` was run against the app's actual light/dark card surfaces (teal converted from its OKLCH token to hex first — Canvas 2D `fillStyle`/`getImageData` was used to resolve that, since `getComputedStyle` echoes `oklch(...)` back verbatim in this Chromium rather than normalizing it). Teal fails the validator's chroma-floor/lightness-band checks, but those two checks are explicitly scoped to *categorical* (multi-series identity) safety per the script's own output footer — meaningless for a lone series. What actually matters for one line — contrast vs. surface — passes at ≥3:1 in both modes. Reusing the app's established brand color (already every button and active nav state) keeps the whole app visually cohesive instead of introducing an unrelated hue.
- **`getAccountBalance`/`getLatestValuation`/`listCashFlowsForHolding`/`getHoldingValue` all grew an optional trailing `asOfDate` param, defaulting to "no filter" (current)**: point-in-time net worth needs the exact same balance/valuation/accrual logic the rest of the app already uses for "now," just parameterized by an arbitrary past date instead of hardcoded to today — so `service/net-worth.ts` calls the *same* functions everything else does (`getAccountBalance`, `getHoldingValue` via a new `getTotalHoldingsValue`) rather than a parallel historical-calculation path that could drift out of sync.
- **`ChartCard` (`src/components/ui/chart-card.tsx`) is generic over its row type** (`ChartCard<T>`), not finance-specific — DESIGN.md already earmarks it as shared infra ("finance, health, and mood charts all read as one consistent system"), so it takes `tableData`/`tableColumns` with a `render` function per column rather than assuming any particular shape. First consumer is `net-worth-chart.tsx`; expect health/mental modules to reuse it directly once they build trend charts.
- **A real, validated 8-slot categorical palette now lives at `--chart-1` through `--chart-8` in `globals.css`, replacing shadcn's 5 auto-generated (and never validated) defaults**: values are the dataviz skill's own reference hues (`references/palette.md`), already proven to pass every adjacent-pair CVD/normal-vision/contrast check in both modes — not run through the validator again here since they're the skill's own pre-validated instance, just copied in as plain hex (not converted to this file's usual `oklch()` — CSS doesn't require one color function per file, and converting risked drifting off the exact validated values). First consumer is the allocation breakdown's stacked bar; any future multi-series chart in this app should pull from this same 8-slot set rather than inventing new hues.
- **Settings + allocation targets are scoped entirely to finance (`finance_settings`, single fixed-`id=1` row; `finance_allocation_targets`, unique per asset class)** — the PRD says "an optional age/DOB field in settings," but no cross-module settings system exists yet and building one wasn't in scope for this step. If health/mental/plans later want their own persisted preferences, this finance-local pattern (a singleton settings row, upserted via `onConflictDoUpdate`) is the template — promote to a shared `core` settings table only once a second module actually needs one, not preemptively.
- **Allocation "current %" uses a coarser equity/debt/gold/cash taxonomy than the "current allocation" breakdown's fine-grained per-type one**, because the age-based suggested-target heuristic only produces four buckets. `COARSE_MAP` (`service/allocation.ts`) folds every unit-priced/accrual investment type into equity or debt; only `gold` and `cash` map 1:1. This is a judgment call, not a PRD-specified mapping — a domestic *debt* mutual fund would currently count as "equity" here, since holdings don't carry a sub-classification. Worth revisiting if bond/debt funds become common in real usage.
- **Allocation percentages return `null` (not a computed number) when net worth is zero or negative, rather than showing the technically-correct-but-nonsensical result of dividing by a non-positive denominator** — caught live: a heavily-leveraged test portfolio (large loan, modest savings) made every single allocation percentage negative, which reads as a broken chart rather than "you're leveraged." The UI falls back to raw values (with an explanatory note) instead of hiding data; the stacked bar itself is only rendered when percentages are meaningful. This is the same defensive pattern as XIRR/CAGR returning `null` on insufficient data rather than a misleading number.
- **The allocation stacked bar is hand-built with flexbox `<div>`s, not Recharts** — Recharts' stacked-`Bar` model has no native way to render the dataviz skill's required 2px surface-color gap between touching segments (only a `stroke`, which the skill explicitly says never to use as a separator: "a stroke adds data-weight ink that isn't data"). A single part-to-whole bar is simple enough that plain flexbox with a real `gap` utility hits the spec exactly, and it's still `ChartCard`-wrapped so the table-view/empty-state contract stays consistent with every Recharts-based chart on this page.
- **An uncontrolled `<Input defaultValue={...}>` needs a `key` tied to the underlying value to pick up a change after a Server Action revalidates** — caught live via a real Base UI console warning ("changing the default value state of an uncontrolled FieldControl after being initialized") on both the DOB field and each editable target-percentage input: after a successful save, the server-computed `defaultValue` prop changes, but React only honors `defaultValue` on a field's *first* mount, so the same DOM node silently keeps its stale value without a `key` forcing a remount. Fixed with `key={settings?.dateOfBirth ?? "none"}` / `key={row.targetPercentage}`. Worth checking for on any future uncontrolled input whose default comes from data a Server Action can change.
- **Capital gains FIFO matches on cash-flow *dollar amounts*, not units** — this schema (deliberately, per `investments.md`) never stores per-transaction units, only a single running `units` total on the holding. `computeFifoGains` (`service/tax.ts`) treats each contribution's dollar amount as its cost-basis "lot," and a redemption consumes the oldest lots' cost first (return of capital, no gain); only the portion of a redemption's proceeds *beyond* the matched cost basis is gain, split across the touched lots in proportion to how much of each lot's cost was consumed, each portion's own lot-date deciding LTCG vs. STCG. Verified live against a hand-computed two-lot scenario (two contributions of different ages, one redemption spanning both) and it matched exactly. **Known limitation, by construction**: this model can only ever produce a gain ≥ 0 per redemption — a redemption below its matched lots' cost basis registers as a zero-gain "return of capital" event, never a realized loss, since there's no unit count to know what fraction of a lot was actually sold at a loss vs. still held. Worth flagging to a user relying on this for loss-harvesting; fixing it for real would mean adding unit tracking to the ledger.
- **Capital gains only run over `UNIT_PRICED_TYPES` (equity, intl_equity, mutual_fund_domestic, mutual_fund_intl, bond, gold) — FD/RD/chit fund/govt scheme "redemptions" are deliberately excluded**, since their payouts are interest/other income under Indian tax law, not capital gains, and running FIFO on them would misclassify that income. Within `UNIT_PRICED_TYPES`, only `equity` and `mutual_fund_domestic` get the special equity LTCG/STCG rates and exemption (`EQUITY_RATE_TYPES` in `service/tax.ts`) — international equity, international mutual funds, bonds, and gold all use the "other" (debt-like) rates, matching how these are actually taxed in India.
- **80C eligibility on a holding is one generic `is_80c_eligible` boolean, not the PRD's literally-named `is_elss`/`is_tax_saver` per-type flags** — mirrors the exact pattern `insurance_policies.is_80c_eligible` already established. Real 80C eligibility for government schemes varies by the specific scheme (PPF/NSC/SSY qualify, KVP/SCSS's status is murkier) in ways this app has no reliable way to auto-detect from a scheme name, so the user marks eligibility themselves on any holding — govt scheme, ELSS fund, or tax-saver FD alike — rather than the app guessing and getting it wrong.
- **80C/80D premium contributions only count for insurance policies linked to a recurring rule with actual confirmed transactions** — an eligible policy with no linked rule contributes nothing to the utilization total, by design: the app has no other reliable trail of *when* and *how much* premium was actually paid (the policy's `premium_amount` alone doesn't confirm payment happened). This is a second concrete payoff of insurance.md's recurring-rule linkage (the first being the shared "Due" worklist) — worth mentioning to a user whose 80D number looks lower than expected.
- **Section 87A rebate is modeled as a flat cutoff (`rebate_87a_threshold_old`/`_new` in tax_settings), not the real law's marginal relief above the threshold** — a taxable income of ₹1 over the threshold gets zero rebate here (a real, if small, accuracy cliff right at the boundary) rather than the graduated relief the actual rule provides. Flagged rather than silently accepted: omitting 87A entirely would have been a much larger error (materially wrong verdicts for a large share of real incomes), so the flat-cutoff version was judged the better tradeoff, but it's still an approximation worth knowing about near the threshold.
- **`finance_tax_slabs`'s NULL-topped bracket needs an explicit `CASE WHEN ... IS NULL THEN 1 ELSE 0 END` in its `ORDER BY`** — SQLite's default is NULLS FIRST for ascending order, which would put the uncapped top bracket at the front of the list instead of the back. Same NULLS-LAST need would apply to any future "open-ended top bucket" table ordered by its bound.
- **The tax settings form's remount `key` uses the *displayed values* joined together, not `updated_at`** — the singleton-row `updated_at` timestamp column is SQLite `current_timestamp` (second-level resolution); two saves inside the same second produce an identical timestamp, silently defeating a timestamp-based remount key and reproducing the exact same stale-`defaultValue` warning the key was meant to fix (caught live). A content-derived key doesn't have that failure mode.
- **Goal composition landed on the existing flat `/plans` list page (each goal row shows its linked holdings inline), not a new `/plans/[id]` detail route** — the PRD explicitly leaves the location open ("in `app/plans` or `app/dashboard`"), and `plans` is still the Phase 1 skeleton (Phase 3 hasn't deepened it yet). Building real per-goal detail routing is Phase 3's job, not this finance step's; the inline-row approach proves the exact composition the PRD asks for (`finance.getHoldingsByGoalId()` called from the `app/` layer, never a plans→finance or finance→plans module import) without preempting a routing decision Phase 3 should make with fuller context.
- **`recurring_rules.linked_goal_id` has the same schema + form field as holdings, but no dedicated "goal detail" query/display of its own** — the PRD's cross-reference rule is written for both tables ("investment_holdings (and recurring_rules) get a nullable linked_goal_id"), and leaving it schema-only with no way to *set* it would make it dead weight, so `RecurringRuleForm` got the same optional "Linked goal" select as `HoldingForm`. But the PRD's one concrete example (`getHoldingsByGoalId()`, composed on a goal's detail view) only names holdings — a symmetrical `getRecurringRulesByGoalId()` wasn't built since nothing in this step calls for it yet; add it if a future feature (e.g. "recurring SIP toward this goal" on the plans side) actually needs it.
- **No "edit holding" action exists yet, so linking an *existing* holding/rule to a goal after the fact isn't possible from the UI** — every finance form in this app so far is append-only (add account, add transaction, add budget, etc.), consistent with the rest of the module, so goal-linking followed the same pattern: set at creation time only. Verified live by creating a fresh holding with a goal selected up front, not by editing "Test Stock" (an earlier test holding) after the fact. Worth building an edit path later if this turns out to matter in real use — nothing about the schema blocks it.
- **`page.tsx` for `/finance/calculators` stays a server component (metadata + `PageHeader` + a Back link) even though the whole route is otherwise DB-free** — every calculator lives in its own client component instead, matching this codebase's established per-concern file split (one file per form/section everywhere else in finance) rather than one large client page. `Metadata` export also requires a server component, which a top-level `"use client" page.tsx` can't provide.
- **The three new growth-formula helpers (SIP, lumpsum, inflation) live in `service/returns.ts`, not a new file** — the PRD calls them "a couple of pure growth-formula helpers" without naming a home; `returns.ts` already held `computeCagr` (the same closed-form compounding idea) so extending it kept every growth/return calculation in one place rather than splitting closely related math across files. `computeEmiAmount` (derives the EMI itself from principal/rate/tenure) went into `service/loans.ts` instead, alongside the schedule functions it feeds — the real Debts view never needs it (EMI is an account field the user already entered there), so it's calculator-only.
- **The XIRR calculator reuses `computeXirr` (the exact same function real holdings call) by passing `currentValue: 0`, rather than calling the `xirr` package directly** — `computeXirr` always appends a synthetic "as of today" inflow for the real-holdings use case; a zero-amount flow contributes nothing to the sum being solved (verified: `0 × (1+r)^Y` is 0 regardless of `Y`), so it's a mathematically inert no-op here. This was the deciding factor for satisfying the PRD's explicit "same solver as real holdings" over writing a bespoke sandbox variant. One side effect worth knowing: the calculator's two default rows are both dated "today," which the underlying `xirr` package rejects (all cash flows on the same day) — it correctly shows "—" until a user changes a date, exactly like the real "not enough data" case elsewhere in this app, not a bug.
- **Rule functions return `Insight[]`, not the PRD's literal `Insight | null`** — several rules (duplicate-transaction groups, stale valuations, budget headroom, insurance lapse, credit utilization) can legitimately fire more than once in the same run (multiple stale holdings, multiple over-limit cards, etc.), and a uniform array return let `engine.ts` compose every rule with one `flatMap` instead of branching on which rules are single- vs. multi-instance. Each rule file is still "one small pure function per rule" in spirit — this only widens the return type.
- **Rules are grouped into three category files (`auditor.ts`/`advocate.ts`/`compliance.ts`), not 15 one-function-per-file modules** — the PRD's "adding a rule is just adding one function and registering it" is satisfied either way (`engine.ts` imports one array per category and spreads them), but 15 near-empty files for functions this small would have fragmented more than it clarified. Split further if any single category file grows unwieldy.
- **`FinanceSnapshot` is assembled once per engine run by calling sibling service functions directly (`../accounts`, `../investments`, `../tax`, etc.), not a fresh set of insights-specific queries** — this is intra-module reuse (everything imported lives inside `finance`), not a cross-module import, so it doesn't touch the module-boundary rule at all. The upside proved out live: every rule's numbers matched the same values already showing on `/finance/investments`, `/finance/debts`, and `/finance/tax`, because they're computed by the literal same functions — "never two systems saying different things," per the PRD, wasn't just a goal but a mechanical consequence of this structure.
- **Insurance-lapse detection reuses the due-worklist's own "unconfirmed periods" signal (`ruleIdsWithDueItems`) instead of a fresh per-policy payment-history query** — "past renewal date with no logged premium" and "linked recurring rule still has due periods" turned out to be the same underlying fact for a policy that tracks its premium through a recurring rule, so a second query would have been redundant. A policy with *no* linked rule is flagged on the renewal date alone, since that's the only signal available for it (documented in step 6's notes as the existing tradeoff of unlinked policies).
- **`ltcgApproachingRule` deliberately stays silent once the exemption is already exceeded (`taxEquityLtcg > 0`)** — that state is the tax estimate's own job to surface (its nonzero tax number already says so on `/finance/tax`), so this compliance rule only covers the "still under, but getting close" window. Firing both would be two insights making the same point with different words, which the PRD's "never two systems saying different things" principle argues against even when the two systems agree.
- **All 15 rules and both new tables (`finance_dismissed_insights`, `finance_insights_settings`) were verified against this session's real accumulated test data, not fresh seed data** — every fired insight traced back to a specific, independently-checkable fact already established earlier in this same build (the Car Loan/Visa interest rates from step 4, the SBI FD rate from step 7, the HDFC Ergo policy's accidental link to the Rent rule from step 6, Visa's credit limit and balance). This incidentally caught two real gaps in the test data itself (Test Stock and Retirement Gold never had a valuation recorded) that had gone unnoticed across a dozen prior steps — a small demonstration of the auditor category doing exactly its job.
