## Notable implementation decisions

- **Health's three deepened features were scoped directly with the user via `AskUserQuestion`** (multi-select checkboxes, not open-ended), since `docs/prd/health.md` explicitly says real scope is "intentionally undefined until discussed with the user" — this phase, unlike finance's, has no PRD spec to build against, so guessing would have risked building the wrong thing for genuinely personal health data. Mental health was explicitly deferred by the user (kept minimal), not skipped by assumption.
- **`health_metrics` kept its Phase 1 table name and most columns, gaining `type` (enum) and `unit` (text) via `ALTER TABLE`, not a new table** — the original skeleton's `label`/`value`/`date`/`note` shape was already 90% of what "structured vitals" needed; adding a `type` discriminator (weight/sleep_hours/exercise_minutes/custom) let trending group reliably by metric without a schema rewrite or a data migration for existing rows.
- **Medication "adherence" is a simple daily dose-log count, not a due-worklist engine like finance's recurring rules** — the user's own option description said medications "could tie into a recurring worklist similar to finance's," but that's an optional suggestion, not a requirement, and finance's recurring-rule engine (FIFO period generation, a `frequency` enum, due/logged reconciliation) is substantial infrastructure that a private `health` module can't reuse (modules never import each other). `frequency` is stored as a free-text reference note only; "logged N doses today" is the whole adherence signal for now. Worth revisiting with a real worklist if daily-granularity turns out to be insufficient in practice.
- **`ChartCard` (`src/components/ui/chart-card.tsx`) was reused as-is for the vitals trend chart** — it was already built generic/finance-agnostic in Phase 2 specifically so health and mental could reuse it directly, per DESIGN.md's "finance, health, and mood charts all read as one consistent system." This is that reuse actually happening, not just a documented intention.
- **Plans' three deepened features were also scoped directly with the user via `AskUserQuestion`**, for the same reason as health — `docs/prd/plans.md` leaves real scope undefined pending user input. The user chose to deepen health, plans, and (deferred) mental "all now, in order."
- **A goal's `type` decides which progress source is authoritative, not a UI toggle** — `financial` goals compute progress from `finance.getHoldingsByGoalId(goal.id)` against `targetAmount` (composed at the `app/` layer, same cross-module pattern as Phase 2 step 12); `other` goals store a manually-updated `progressPercent`. The column is nullable and only meaningful for one type at a time — set at creation and left alone after, since goals don't change type once created.
- **Priority sort is a SQL `CASE` expression (`PRIORITY_RANK`) passed straight to `.orderBy()`, not application-side sorting** — mirrors the precedent from `finance/db/queries/tax-slabs.ts` (Phase 2 step 11) for ordering by an enum's logical rank rather than its alphabetical text value.
- **No goal-edit UI beyond progress updates** — matches the append-only-creation-plus-targeted-edits pattern established in Phase 2 (e.g. tax slab rates, allocation targets): a goal's name/type/priority/target are set at creation; only the field expected to change over time (progress) gets its own inline edit form.
